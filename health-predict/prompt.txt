# Build a Type 1 Diabetes Glucose Prediction System

## Objective

Build a research-grade machine-learning system that predicts future glucose levels for a person with Type 1 Diabetes using approximately **365 days of historical CGM and insulin data**.

The initial objective is **glucose prediction only**.

Do **NOT** make insulin dosing recommendations, treatment recommendations, or automated therapy decisions.

The system should predict glucose at multiple future horizons:

* 15 minutes
* 30 minutes
* 45 minutes
* 60 minutes

The architecture should allow additional horizons to be added later.

The system must be designed so that the model can be rigorously evaluated using historical data and avoid data leakage.

# 2. Input Data

The system will receive historical diabetes data covering approximately 365 days.

At minimum we expect:

### CGM

Typical fields:

```text
timestamp
glucose
```

Glucose is expected to be in:

```text
mmol/L
```

The system must support configurable CGM sampling intervals, particularly:

* 5 minutes
* 10 minutes
* 15 minutes

Do not assume the data is perfectly regular.

### Insulin

Insulin data may contain:

```text
timestamp
insulin_units
insulin_type
delivery_type
```

Possible delivery types include:

* basal
* bolus
* correction
* automated basal adjustment

If the source data has different terminology, create a configurable mapping layer rather than hard-coding assumptions.

### Optional future inputs

Design the architecture so that the following can be incorporated later:

* carbohydrate intake
* meals
* exercise
* sleep
* illness
* stress
* heart rate
* activity
* insulin sensitivity
* insulin-to-carb ratio
* basal profile
* insulin-on-board
* meal annotations

Do not require these fields for the first version.

# 5. Important Data Leakage Requirement

This is critical.

The model must NEVER use information that would not have been available at prediction time.

For example, when predicting glucose 30 minutes into the future:

```text
prediction_time = T
target = glucose at T + 30 minutes
```

Features may only use information available at or before `T`.

Do NOT use:

* future glucose values
* future insulin
* future carbohydrate information
* future-derived rolling statistics
* centered rolling windows
* future interpolation
* future normalization information

Be especially careful with preprocessing and feature engineering.

Document all leakage-prevention decisions.

# 6. Prediction Targets

Create separate targets for:

```text
glucose_15m
glucose_30m
glucose_45m
glucose_60m
```

For example:

```text
timestamp        current_glucose    glucose_15m    glucose_30m
10:00            7.2                7.8            8.6
10:05            7.4                8.1            9.0
```

Also create delta targets:

```text
delta_15m
delta_30m
delta_45m
delta_60m
```

where:

```text
delta_30m =
future_glucose_30m - current_glucose
```

Evaluate both approaches:

1. Direct glucose prediction
2. Glucose-delta prediction

Determine empirically which performs better.

# 7. Feature Engineering

Build features from information available up to the prediction timestamp.

## A. Current glucose

Include:

```text
current_glucose
```

## B. Glucose history

Create lag features for approximately:

```text
5m
10m
15m
20m
30m
45m
60m
90m
120m
180m
```

For example:

```text
glucose_lag_5m
glucose_lag_10m
glucose_lag_15m
...
```

## C. Glucose velocity

Calculate:

```text
glucose_change_5m
glucose_change_10m
glucose_change_15m
glucose_change_30m
```

Also calculate rates:

```text
mg/dL/min equivalent
mmol/L/hour
```

Use mmol/L as the primary internal unit.

## D. Acceleration

Calculate:

```text
velocity_5m
velocity_10m
velocity_15m
acceleration
```

This is important because a glucose value of 8 mmol/L can have very different future trajectories depending on whether glucose is:

```text
8 → 7.5 → 7.0
```

or

```text
8 → 8.5 → 9.0
```

## E. Rolling statistics

Calculate trailing:

```text
mean
median
std
min
max
range
slope
```

over:

```text
15m
30m
60m
120m
180m
```

Only use trailing windows.

## F. Time-of-day

Create:

```text
hour
minute
day_of_week
day_of_year
is_weekend
```

Use cyclical encoding:

```text
sin_hour
cos_hour
sin_day_of_week
cos_day_of_week
```

## G. Insulin features

Create insulin features over trailing windows:

```text
insulin_last_15m
insulin_last_30m
insulin_last_60m
insulin_last_90m
insulin_last_120m
insulin_last_180m
insulin_last_240m
```

Also:

```text
basal_insulin_last_30m
basal_insulin_last_60m
bolus_insulin_last_30m
bolus_insulin_last_60m
bolus_insulin_last_120m
```

Create time-since-last-bolus:

```text
minutes_since_last_bolus
```

and:

```text
last_bolus_amount
```

If insulin delivery is granular enough, calculate an estimated insulin-on-board feature.

Clearly document the assumptions used.

# 8. Insulin-On-Board

# 11. Train/Validation/Test Strategy

DO NOT randomly split the time-series data.

Use chronological splitting.

For example:

```text
First 70%  = training
Next 15%   = validation
Last 15%   = test
```

Better yet, implement rolling-origin evaluation.

Example:

```text
Train: months 1–6
Validate: month 7

Train: months 1–7
Validate: month 8

Train: months 1–8
Validate: month 9
```

The final test set must remain untouched until model selection is complete.

Avoid leakage caused by overlapping windows across train/test boundaries.

Document the exact split strategy.

# 30. Critical Design Principle

Start simple.

The goal is NOT to create the most complicated neural network.

The goal is to determine:

> "Given everything that was known at time T, how accurately can we predict this person's glucose at T+15, T+30, T+45 and T+60 minutes?"

Every model must be compared against a simple persistence baseline.

If XGBoost achieves:

```text
15m MAE = 0.35 mmol/L
30m MAE = 0.55 mmol/L
```

while an LSTM achieves:

```text
15m MAE = 0.36 mmol/L
30m MAE = 0.56 mmol/L
```

prefer XGBoost.

Accuracy, robustness, interpretability and absence of leakage are more important than model complexity.
